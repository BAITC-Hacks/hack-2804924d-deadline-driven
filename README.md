# Beeline Campaign AI — Deadline Driven

Агент планирования тарифных маркетинговых кампаний для кейса HackAlem AI.
Он исследует синтетическую аудиторию, проверяет гипотезы пилотами и формирует
план кампаний с учётом стоимости каналов, бюджета и лимита контактов.
Основной пользователь — аналитик маркетинга.

## Состояние проекта

- Python-агент, API, финансовый отчёт, экспорт CSV и сохранение запусков работают в ветке `backend-api`.
- Улучшенная стратегия из `agent-strategy` объединена с бэкендом.
- В проверенной версии `main` опубликована папка `frontend`, но отсутствует `backend`.
- Фронтенд в этой версии `main` является демонстрацией: данные заданы в `src/App.tsx`, запуск имитируется таймером, CSV собирается из примеров. Запросов к API в нём нет.
- Для полноценной версии необходимо опубликовать подключённый к API фронтенд и объединить обе части в одной ветке. Локальная версия участника может отличаться от опубликованной.

Все данные кейса синтетические. Результаты мок-среды не являются реальными
показателями Beeline и не предсказывают балл скрытого судейства.

## Возможности бэкенда

- Асинхронный запуск расчёта и получение статуса по `run_id`.
- Выбор аудиторий, целевых тарифов и каналов коммуникации.
- История шумных наблюдений пилотов и оценка результата мок-скорингом.
- Финансовые показатели, охват и остатки ресурсов.
- CSV из результата того же запуска, без повторного вызова агента.
- Восстановление результатов после перезапуска сервера.

## Архитектура

```text
React + TypeScript + Vite
          │ HTTP: запуск, статус, результат, CSV
          ▼
FastAPI → очередь одного исполнителя → Agent.act(env)
          │                              │
          │                        пилоты мок-среды
          ▼                              ▼
JSON-хранилище ← отчёт и оценка общего плана
```

HTTP-связь с фронтендом — целевая интеграция; её наличие нужно проверить в
актуальной опубликованной версии интерфейса, а не по анимации кнопки запуска.
Агент для сдачи работает отдельно от FastAPI и React.


Для текущего бэкенда выберите `git switch backend-api`. Для опубликованного

## Запуск на Windows

Нужны Python с модулем `venv`, Node.js с npm и Git. Бэкенд проверялся на
Python 3.14.3; версии библиотек закреплены в `backend/requirements.txt`.
Для фронтенда используйте версию Node.js, совместимую с engines зависимостей
в `frontend/package-lock.json`; установка выполняется через `npm ci`.

### Терминал 1 — бэкенд

Из корня репозитория:

```powershell
cd backend
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn api:app --reload
```

Активация окружения не обязательна: команды используют его Python напрямую.
Запускайте из `backend`, поскольку инструменты оценки читают относительные пути.

- API: http://127.0.0.1:8000
- Проверка доступности: http://127.0.0.1:8000/health
- Интерактивная документация: http://127.0.0.1:8000/docs

### Терминал 2 — фронтенд

Из корня копии репозитория с папкой `frontend`:

```powershell
cd frontend
npm ci
npm run dev -- --host localhost --port 5173 --strictPort
```

Откройте http://localhost:5173. `--strictPort` не позволяет незаметно перейти
на другой порт, для которого ещё не настроен CORS.

Команды фронтенда из package.json:

```powershell
npm run build
npm run lint
npm run preview
```

`preview` служит для просмотра сборки; его origin необходимо отдельно разрешить
в CORS при проверке API. Успешная сборка не подтверждает интеграцию с сервером.

### Подключение API

Базовый адрес для фронтенда на том же компьютере: `http://127.0.0.1:8000`.
Бэкенд разрешает origins `http://localhost:5173` и `http://127.0.0.1:5173`.
В опубликованном демонстрационном интерфейсе переменная адреса API ещё не реализована.
Не добавляйте выдуманные переменные .env: сначала согласуйте их с разработчиком фронта.

Каждый участник может запускать обе части у себя. `127.0.0.1` всегда указывает
на собственный компьютер пользователя, а не на компьютер другого участника.

## Сценарий работы с API

1. Вызвать `POST /runs` и сохранить `run_id` из ответа 202.
2. Опросить `GET /runs/{run_id}` примерно раз в секунду.
3. При `completed` запросить `/result`; при `failed` показать `error` и остановить опрос.
4. Показать кампании, показатели и пилоты полученного запуска.
5. Скачать `/submission` по тому же ID.
6. После перезапуска сервера проверить доступ к завершённому запуску по прежнему ID.

## Маршруты

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/health` | Проверка доступности |
| POST | `/runs` | Создание фонового запуска, HTTP 202 |
| GET | `/runs/{run_id}` | Статус и ошибка |
| GET | `/runs/{run_id}/result` | Сохранённый результат |
| GET | `/runs/{run_id}/submission` | CSV того же результата |
| POST | `/preview` | Отдельный синхронный расчёт без сохранения |

Статусы: `queued`, `running`, `completed`, `failed`.
Неизвестный ID даёт 404; недоступный до завершения результат — 409.
В Swagger список возможных ошибок под ответом не означает, что запрос завершился ошибкой.

## Поля отчёта

| Поле | Значение |
|---|---|
| `environment` | `mock` — локальная демонстрационная среда |
| `campaign_count` | Количество финальных кампаний |
| `campaigns` | Финальный план и фильтры сегментов |
| `pilots` | Шумные наблюдения пилотов |
| `metrics.net_arpu_gain` | Чистый прирост после расходов |
| `metrics.total_cost` | Расходы пилотов и финального плана |
| `metrics.remaining_budget` | Итоговый остаток бюджета |
| `metrics.total_contacts` | Все контакты, включая повторные |
| `metrics.unique_customers_targeted` | Уникальные абоненты |
| `metrics.remaining_contacts` | Итоговый остаток контактов |
| `metrics.n_pilots` | Количество пилотов |
| `metrics.n_campaigns` | Пилоты плюс финальные кампании |
| `campaign_details` | Детали мок-скоринга каждой кампании |
| `after_pilots` | Остатки после разведки, до финального плана |

`metrics.status` PASS/FAIL обозначает знак финансового результата, а не статус
выполнения запроса. ROI при нулевых затратах равен null.
`observed_lift_ratio` — доля; для процентов умножайте на 100.
Поля с суффиксом `_pct` уже выражены в процентах.
Наблюдения пилотов и эффекты оценщика различаются из-за шума. Сумма эффектов
отдельных кампаний может отличаться от общего эффекта из-за пересечений аудиторий.

## Как работает агент

1. Из истории переходов строит предварительные оценки и ранжирует гипотезы.
2. Делит целевую аудиторию на сегменты, выразимые фильтрами среды.
3. Проводит пилоты с учётом доступных ресурсов и сохраняет резерв для итогового плана.
4. Обновляет оценки эффекта и неопределённости по наблюдениям.
5. Выбирает кампании с положительной консервативной оценкой и доступными ресурсами.
6. Рассматривает улучшения каналов; при отсутствии положительного плана использует допустимый резервный вариант.

История описывает другую выборку, поэтому не заменяет пилоты. Основная стратегия
оценивает перенос эффекта между каналами по публичным множителям; это приближение,
а не прямая проверка каждого выбранного канала. Подробнее: [стратегия](backend/STRATEGY.md).

## Ограничения кейса

| Ограничение | Значение |
|---|---:|
| Финальные кампании | 1–10 |
| Абоненты на кампанию | до 5 000 |
| Контакты, включая пилоты | до 15 000 |
| Общий бюджет | 100 000 у.е. |
| Пилоты | до 20 |
| Размер пилота | 10–200 |

Эффект засчитывается по уникальным абонентам, повторные контакты расходуют ресурсы.
Пилоты входят и в расходы, и в оценку результата. Требования и ограничения среды
описаны в [руководстве кейса](backend/PARTICIPANT_GUIDE.md).

## Сохранение и ограничения сервиса

Результаты записываются в `backend/storage/runs/<run_id>.json` атомарной заменой.
После перезапуска завершённые результаты восстанавливаются. Незавершённые записи
`queued/running` становятся `failed` с объяснением. CSV строится из сохранённого
отчёта. Данные storage не коммитятся и не передаются другим участникам через Git.

Сервис — локальный прототип: один процесс Uvicorn, последовательные фоновые
расчёты, нет авторизации, ограничения длины очереди и принудительного тайм-аута
процесса агента. Не запускайте несколько серверов с общей папкой storage.

## Команда

Deadline Driven:

- Frontend: интерфейс, отображение данных и экспорт через API.
- Backend: запуск агента, отчёт, хранение и интеграция.
- Data / Agent: гипотезы, стратегия пилотов, оптимизация и оценка устойчивости.

Рабочие ветки объединяются через проверенные pull request. Финальная ветка должна
содержать обе части проекта и соответствовать инструкции запуска.
