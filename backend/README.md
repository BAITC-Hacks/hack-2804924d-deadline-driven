# HackAlem — Beeline Campaign Agent

Python-бэкенд для демонстрации агента тарифных маркетинговых кампаний.
Данные синтетические, предоставлены в пакете хакатона.
Текущий agent.py — базовый шаблон, стратегия пока не улучшена.

## Запуск на Windows

Откройте PowerShell в корне клонированного проекта:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn api:app --reload
```

Документация API: http://127.0.0.1:8000/docs
Все команды выполняются из корня проекта: данные читаются по относительным путям.

## Подключение фронтенда

Каждый разработчик запускает бэкенд у себя. Адрес API: http://127.0.0.1:8000
CORS разрешает http://localhost:5173 и http://127.0.0.1:5173.

1. POST /runs возвращает run_id (HTTP 202).
2. GET /runs/{run_id} — опрос раз в секунду до completed или failed.
3. GET /runs/{run_id}/result — кампании завершённого запуска.
4. GET /runs/{run_id}/submission — CSV того же запуска.

GET /health проверяет доступность. POST /preview выполняет отдельный синхронный расчёт.
Статусы: queued, running, completed, failed. При failed доступно поле error.
Неизвестный run_id даёт 404, ещё не готовый результат — 409.

## Ограничения прототипа

Запуски сохраняются в backend/storage/runs/*.json и восстанавливаются при перезапуске. Путь определяется относительно api.py.
Используйте один процесс Uvicorn, без нескольких workers.
API работает с мок-средой; результат не предсказывает балл судейства.
API возвращает кампании, историю пилотов и финансовый отчёт мок-среды одного запуска.
Сервис предназначен для локальной разработки; авторизация и постоянное хранилище не реализованы.

## Проверка и сдача

```powershell
.\.venv\Scripts\python.exe local_eval.py
.\.venv\Scripts\python.exe local_eval.py --runs 10
.\.venv\Scripts\python.exe make_submission.py
```

Для сдачи нужны agent.py, submission.csv и зависимости; API не требуется для запуска агента.
Отрицательный результат базового шаблона означает убыточную стратегию, а не сбой API.


## Поля результата для фронтенда

Существующие campaign_count и campaigns сохранены. Добавлены:
- pilots: наблюдения пилотов (observed_lift_ratio, observed_lift_total, n_customers, cost).
- metrics: итоговый скоринг мок-среды с учётом пилотов и финальных кампаний.
- metrics.net_arpu_gain: чистый прирост; total_cost: затраты; total_contacts: контакты.
- metrics.remaining_budget и remaining_contacts: остатки ПОСЛЕ всех кампаний.
- metrics.n_pilots: число пилотов; unique_customers_targeted: уникальные абоненты.
- metrics.status: PASS/FAIL означает знак финансового результата, а не статус исполнения API.
- after_pilots: остатки только после разведки; не путать с итоговыми metrics.
- campaign_details: детали всех кампаний, сначала пилотных, затем финальных.

Наблюдения pilots шумные; campaign_details показывает оценку мок-скоринга.
Сумма gross_lift из деталей может отличаться от общего прироста из-за пересечений аудиторий.
ROI при нулевых затратах представлен null. Все числа относятся к мок-среде, не к судейству.

Проверка отчёта: python -m unittest test_run_report -v (из папки backend).


## Сохранение запусков

Завершённые и неуспешные запуски восстанавливаются по прежнему run_id.
Если при остановке оставались queued/running, после старта они получают failed с объяснением.
Запись JSON атомарная: временный файл заменяет прежний только после успешной записи.
Повреждённые файлы пропускаются с ошибкой в журнале, остальные запуски доступны.
CSV создаётся из сохранённых кампаний без повторного вызова агента.
Папка storage исключена из Git. Используйте один процесс сервера; несколько серверов не должны совместно использовать эту папку.
POST /preview остаётся отдельным несохраняемым предварительным расчётом.
Запуски, сделанные до добавления сохранения, восстановить нельзя.

Проверки: python -m unittest test_run_report test_run_storage -v
Ручная проверка: создайте запуск, дождитесь completed, сохраните run_id, перезапустите сервер и запросите result и submission по тому же ID.
