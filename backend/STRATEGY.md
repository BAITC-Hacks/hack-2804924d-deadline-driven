# Deadline Driven — стратегия тарифных кампаний

Рабочий агент участника №3 для синтетического кейса Beeline. Точка входа:
`agent.py`, класс `Agent`, метод `act(env)`. Фронтенд и FastAPI для запуска
и сдачи не требуются. Агент не использует сеть, LLM или секретные параметры среды.

Сравнение со стартовым решением на **20 seed**, эксперимент с подтверждением
дорогих каналов и сценарий защиты — в [BENCHMARK.md](BENCHMARK.md).
Основным остаётся `agent.py`: эксперимент `agent_confirmed.py` на официальной
мок-среде менее результативен, поэтому автоматически не используется.

## Запуск

Из корня распакованного пакета участника, где лежат `customer_profile.csv`,
`data/`, официальные `local_eval.py` и `make_submission.py`:

```shell
python -m pip install -r requirements.txt
python -m unittest -v test_agent.py test_validation.py test_agent_confirmed.py
python verify_submission.py --runs 10
python export_demo.py
python local_eval.py
python local_eval.py --runs 10
python make_submission.py
```

Сдача: `agent.py`, сгенерированный `submission.csv`, `requirements.txt`.
Агент читает только разрешённую историю `data/change_tariff.csv` относительно
своего файла и публичные свойства `env`. Если истории нет, работает с нейтральными
начальными оценками и пилотами. Пакет организаторов нужен для локальной проверки;
скрипты организаторов не изменялись. Для повторения проверенной комбинации
библиотек используйте `requirements-tested.txt`. Python 3.11+ рекомендуется
для этих закреплённых версий; Python должен быть установлен отдельно.

`verify_submission.py` проверяет исходный план без молчаливого удаления ошибок,
точное соответствие фильтров аудитории, непересекаемость кампаний, все лимиты,
официальный PASS и воспроизводимость CSV. Результат сохраняется в `verification.json`.
Исправления и оставшиеся ограничения описаны в [HARDENING.md](HARDENING.md).

## Алгоритм

1. Сформировать непересекающиеся сегменты «текущий тариф × ARPU». Сегменты
   больше 5000 разделить по потреблению интернета и звонков. Если поддерживаемых
   фильтров недостаточно, такой сегмент пропустить, не обрезая произвольно строки.
2. По истории оценить относительные изменения ARPU для каждого перехода.
   Ограничить влияние экстремальных отношений, уменьшить влияние малых выборок.
   Эти наблюдения относятся к другой аудитории и не являются оценкой причинного
   эффекта коммуникации. Они используются как слабое начальное знание и для
   выбора до трёх гипотез на сегмент. Конкретные тарифы в решениях не зашиты.
3. Выбрать недорогой информативный канал по публичным множителям и стоимости.
   Сначала проверять разные гипотезы по 150 человек, затем выбирать повторные
   проверки по потенциальной ценности и неопределённости, до 200 человек.
   Размер уменьшается, если остаток ресурсов или аудитория меньше.
4. Обновить среднее эффекта по наблюдениям. Шум среднего уменьшается как
   `1/sqrt(n)`; масштаб 0.8 указан в публичном описании среды. Историческая
   начальная оценка имеет малый вес по сравнению с пилотом.
5. Выбрать прибыльные по консервативной оценке кампании в непересекающихся
   сегментах. Учесть стоимость каждого контакта и уже потраченные ресурсы.
6. Проверить улучшение канала выбранных кампаний за оставшийся бюджет.
   Платный канал выбирается, только когда оценённый дополнительный эффект
   больше дополнительных затрат.

Лимит разведки: до четверти исходного бюджета и обычно до четверти исходных
контактов, не более 3000. При малом остатке контактов допускается минимум
10 для пилота, если после него помещается целая финальная кампания. Агент
резервирует бюджет и контакты под минимальный доступный финальный сегмент.
Это настройки базовой стратегии, не
оптимальные константы, найденные под скрытые эффекты. Число пилотов ограничено
публичным остатком, 20 попытками и временем 240 секунд перед следующим пилотом.
Зависший вызов самой среды этот таймер прервать не может.

## Неопределённость и ограничения

- Среда возвращает агрегированный `observed_lift_ratio`. Агент не выдумывает
  индивидуальные результаты или дисперсию из одного агрегата.
- ID пилотных участников не опубликованы. Для оценки прироста финального плана
  используется ожидаемая неохваченная доля `product(1 - n_pilot / n_segment)`.
  Формула учитывает повторный случайный отбор, но остаётся приближением;
  точные ID и уже зачтённые индивидуальные эффекты агенту неизвестны.
  Настоящую дедупликацию выполняет официальный оценщик. Все повторные контакты
  входят в лимиты и оплачиваются, даже если абонент уже встречался в пилоте.
- Перенос эффекта между каналами использует публичные множители. При насыщении
  конверсии это приближение может завышать эффект сильного канала. Следующее
  улучшение — отдельные подтверждающие пилоты дорогих каналов.
- Штраф за неопределённость — эвристика; это не гарантированный доверительный
  интервал. Жадный план не гарантирует глобального оптимума.
- Если ни одна кампания не проходит положительный порог, агент выбирает одну
  доступную с наименьшим оценённым риском, чтобы выполнить обязательный минимум.
  Она может быть убыточной. Если ресурсов вообще недостаточно, выполнить
  обязательный минимум невозможно. Ошибки пилотов журналируются; если все
  вызовы среды завершились ошибкой, условие успешного пилота не может быть выполнено.
- История запусков сбрасывается на каждом `act`; агент не сохраняет скрытые
  ответы между запусками. Используются только публичные входы, история и пилоты.

## Проверка 23 сентября 2026

Библиотеки проверенной среды: NumPy 2.3.5, pandas 3.0.1.

- 26 тестов прошли, включая матрицу из 12 комбинаций бюджета и контактов:
  повреждённые ответы и таймауты пилотов, сохранение ресурсов под финал,
  соответствие отчёта реальным аудиториям, повторная выборка и проверка каналов.
- Официальный `local_eval.py`: **PASS**, без отброшенных кампаний.
- Seed 42: 18 пилотов и 3 финальные кампании; 6969 контактов суммарно;
  затраты 99 318 из 100 000; чистый результат **+2 797 314** у.е.
- `local_eval.py --runs 10`: положительный результат **10/10**;
  минимум **+2 241 614**, медиана **+2 757 820**, максимум **+2 897 000**.
- `make_submission.py` запущен дважды: CSV побайтово совпал.

Официальный отчёт показывает 21 кампанию, потому что включает 18 пилотов.
Лимит 10 относится к финальному плану, где 3 кампании. Остатки `env` в конце
отчёта учитывают только пилоты; общий расход указан в блоке скоринга.
Эффекты на судействе другие. Эти цифры подтверждают локальную работоспособность
и устойчивость к шуму мок-среды, а не будущий балл.

## Участнику №2: подключение

```python
from agent import Agent

agent = Agent()
campaigns = agent.act(env)
report = agent.report
```

`report` содержит `pilots`, `campaigns`, `warnings`, `pilot_cost`,
`pilot_contacts`, `final_cost`, `final_contacts`, `runtime_seconds`.
Добавлен блок `resources` с остатками после пилотов и после финального плана.
В каждой кампании есть `estimate_basis` и `channel_confirmed`, позволяющие
различать прямой пилот и перенос эффекта между каналами. `export_demo.py`
сохраняет пример JSON в `demo_report.json` без чтения скрытых эффектов.
В кампаниях есть оценка эффекта и неопределённости — это прогноз, не истинный
результат скоринга. Для каждого параллельного запуска создавайте отдельные
`env` и `Agent`. API, сохранение отчёта и выдача CSV остаются у участника №2.

Для интеграции с обязательной проверкой есть `integration.run_agent(env)`:
он создаёт агента, запускает его один раз, проверяет кампании и возвращает
`campaigns`, `report`, `validation`. При невыполнении требований выбрасывает
`ValueError`, который API должен показать как `failed`, а не `completed`.
`report.requirements` отдельно отмечает наличие пилота, финального плана и
соблюдение лимитов. `report.pilot_errors` содержит ошибки внешних вызовов.

Ранее созданный `beeline_strategy/` — независимый предварительный прототип.
Текущий `agent.py` самодостаточен и его не импортирует: оцениватель переписан
под фактический агрегированный ответ публичного SDK.
