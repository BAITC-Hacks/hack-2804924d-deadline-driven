# Исправления устойчивости агента

Изменения относятся к основному `agent.py` и локальным инструментам проверки.
Данные и оценщик организаторов не изменены. Фронтенд и текущая версия API команды
в этой папке отсутствуют; их сквозная проверка в этот этап не входит.

| Проблема | Исправление | Проверка |

| Сегмент помещался в лимит, но уже не помещался после пилота | Сегментация учитывает доступные контакты и запас для пилота | Аудитория 300 разбивается фильтром на две по 150 |
| Повторные случайные пилоты считались полностью новыми абонентами | Ожидаемая неохваченная доля считается произведением вероятностей не попасть в каждый пилот | Повторная выборка не обнуляет аудиторию без оснований |
| KeyError/TimeoutError после ответа среды обрывал запуск | Ошибки вызова и проверки ответа изолированы, число попыток ограничено | Неполный ответ и таймаут не мешают сформировать допустимый резервный план |
| Повреждённый ответ скрывал уже потраченные ресурсы | Расход читается из публичных счётчиков в finally | Отчёт совпадает с реальным уменьшением бюджета и контактов |

| Исторические бесконечные ARPU влияли на приоритеты | Нефинитные строки исключаются | В анализ попадают только корректные наблюдения |
| Любая ошибка пилота делала объяснение всех кампаний неоднозначным | Причина выбора зависит от использования резервного плана, ошибки журналируются отдельно | Отчёт различает выбор по оценке и вынужденный минимум |
| Пустой план выглядел как обычный результат | Отчёт имеет явные requirements; интеграция не помечает такой запуск успешным | Пустой ресурсный остаток и отсутствие успешных пилотов обнаруживаются |

## Проверки

```shell
python -m unittest -v test_agent.py test_validation.py test_agent_confirmed.py
python verify_submission.py --runs 10
```

26 тестов, включая 12 комбинаций начального бюджета и контактов внутри одного
параметризованного сценария. Проверяются реальные размеры аудиторий по фильтрам,
а не только числа из отчёта. CSV создаётся штатным `make_submission.py` дважды,
сравнивается побайтово и с независимо полученным результатом агента.

Повторное сравнение на seed 0–9 и 100–109 не изменило результаты основного
агента: 20/20 положительных, средний net +2 495 063. Для seed 42 сохранены
3 финальные кампании, 18 пилотов, 6 969 контактов и расходы 99 318.
Подробные численные результаты: `benchmark_results.json`, `benchmark_holdout.json`,
`verification.json`, `validation_seed42.txt`.

## Что остаётся ограничением

- Это эвристический алгоритм: глобальный оптимум распределения бюджета не доказан.
- Исторический выбор трёх тарифов на сегмент может пропустить удачный новый переход.
- Основной агент переносит эффект между каналами по публичным множителям.
  Проверяющая каналы версия сохранена отдельно, но пока проигрывает по среднему
  результату. Нет оснований утверждать, что любая из них лучше на всех скрытых данных.
- Поправка на пересечение пилотов вероятностная, без доступа к реальным ID.
- Если все эффекты отрицательны, обязательные пилоты и минимум одна кампания
  могут привести к убытку. Нельзя гарантировать прибыль или победу на судействе.
- Синхронный вызов среды, который навсегда завис, не прерывается изнутри `act`.
  Для внешнего сервиса нужен timeout процесса запуска. Обычные ошибки вызовов
  обрабатываются, а между вызовами проверяется время.
- При невозможных входах (некорректные ресурсы, дубли ID, пустые каналы) агент
  выдаёт понятную ошибку. Он не выдумывает данные и не скрывает невозможность сдачи.

## Подключение команды

```python
from integration import run_agent

result = run_agent(env)  # один вызов, кампании и отчёт от одного запуска
```

Сохранить `result` в backend и выдавать его фронтенду. Если функция выбросила
ошибку проверки, статус запуска должен стать `failed`. CSV формировать из
сохранённого `result['campaigns']`, не вызывая агента повторно.

Для сайта есть готовый `demo_report.json`, но он относится к seed 42 мок-среды.
Поля `estimated_ratio` и `uncertainty` нельзя подписывать как фактическую прибыль.
